# 标准化产物与生产反馈口径

以下 Spark 固定 8 小时窗口部分记录的是 2026-10-13 的设计。独立 Spark
项目现已改为按标准化正文大小分块；本 Python 部署没有启用时间窗口或字节
分块，分组保持不变。2026-10-14 的前缀索引审计结论见本文末尾。

这次变更同时满足标准化交付和生产反馈汇报需求：保留完整轨迹、隔离原因与
来源记录，并提供批次状态、产物规模、耗时边界和轨迹文本量，便于下游接入、
核对产出和初步筛选。Python 与 Spark 共享下述反馈字段和 token 估算口径；
8 小时分组仅用于独立 Spark 实现，普通 Python 分组保持不变。

## manifest 顶层字段

以下字段位于 `manifest.json` 顶层。原有 `counts`、文件清单和来源信息继续
保留；新字段明确区分产出轨迹数和输入解析失败数，不改变旧计数的含义。

| 字段 | 含义 |
| --- | --- |
| `status` | 成功发布的本批产物为 `"SUCCEEDED"`；允许含隔离轨迹或解析失败记录。 |
| `started_at_ms` | 本次标准化入口开始的 Unix 毫秒时间戳。 |
| `completed_at_ms` | 本次结果完成时记录的 Unix 毫秒时间戳；任务入口包含产物校验时间，底层导出入口记录产物导出完成时间。 |
| `total_bytes` | 最终根目录轨迹 JSONL 文件的实际字节总量，包括 accepted 和 quarantined 轨迹正文。 |
| `record_count` | 最终顶层轨迹条数，等于 `accepted_trajectory_count + quarantined_trajectory_count`。 |
| `accepted_trajectory_count` | 成功写出的、通过当前标准化检查的顶层轨迹条数。 |
| `quarantined_trajectory_count` | 成功写出、但被标准化检查隔离的顶层轨迹条数。 |
| `parse_failure_count` | 输入记录解析失败的数量，不是隔离轨迹数量，也不是 `counts.quarantined_records` 的别名。 |

时间戳使用墙上时钟的 Unix 毫秒；`completed_at_ms - started_at_ms` 可用于
批次处理耗时汇报，不是逐条 capture 的时间。`total_bytes` 不计
`manifest.json`、`lineage.jsonl`、诊断文件、隔离的非轨迹记录、临时文件或
媒体对象。已挂载子代理的内容仍在根轨迹 JSONL 内，因此它们占用的序列化字节
计入该根文件大小。

`record_count` 按最终顶层记录计数：包含作为顶层输出的孤立子代理，但不会
把 `sub_agent_trajectory` 内的已挂载子节点再次计为独立记录，也不按原始
请求数或 lineage 条数计数。解析失败输入与可物化的隔离轨迹分别报告；已经
解析成功但只能作为非轨迹记录输出的输入，也不因此计入 `parse_failure_count`。

没有符合条件的输入时，空批次可以合法发布 `SUCCEEDED` manifest：
`record_count`、`total_bytes`、两个轨迹分类计数及 `parse_failure_count`
均为零，开始和完成时间仍有效。基础设施错误或内部构建异常仍应失败，不能
通过把异常当成空输入来发布成功。

## 每个轨迹节点的 total_tokens

每个根轨迹和已挂载子节点均含非负整数 `total_tokens`。它用现有
`unicode-word-v1` 方法估算本节点的可见文本量，属于内容量指标，不是模型
tokenizer 的精确计数、API usage 或计费 token。

计算本节点自身的消息正文、可见 `reasoning_content`、本地 `instructions`、
工具定义、工具名称/参数，以及可见工具结果。结构化参数、schema 和结果按
确定性的紧凑 JSON 参与估算。原始 reasoning 副本、加密/不透明内容、
agent-message/compaction 侧车、媒体载荷、标识和审计 metadata 不参与估算。

父节点不会累加 `sub_agent_trajectory` 中子节点的 token 数；每个子节点只
计算自己的内容。父节点自身消息中已经出现的 spawn 调用、子任务摘要或工具
结果仍属于父节点内容。已挂载子代理继续嵌套保存，并未新增逐个子代理独立
导出的行为。`reasoning_total_tokens` 继续作为单独的 reasoning 指标保留，
下游不应再把它加到已经包含可见 reasoning 的 `total_tokens` 上。

这些字段可用于规模汇报和长度初筛。accepted 状态与 token 大小都不能单独
证明轨迹适合训练；具体训练任务仍需结合内容、完整性、工具一致性和隔离原因
选择数据。

## Python 与 Spark 的分组边界

普通 Python 版本保持原规则：真实 session 按 session 构建，前缀比较保留
thread 边界；缺失 session（包括字面值 `no_session_id`）按既有用户身份
聚合，可以跨时间窗口折叠已证明的累计前缀。

独立 Spark 版本对缺失 session 增加固定 8 小时窗口。窗口由已有
`captured_at` 表示的时刻转换为北京时间（Asia/Shanghai，此规则固定
UTC+08:00）后确定，用户身份与本地日期共同参与分组：

| 北京时间范围 | 窗口起点示例 |
| --- | --- |
| [00:00, 08:00) | `2026-10-13T00:00:00+08:00` |
| [08:00, 16:00) | `2026-10-13T08:00:00+08:00` |
| [16:00, 次日 00:00) | `2026-10-13T16:00:00+08:00` |

08:00、16:00 和次日 00:00 恰好归入新窗口。等价时区表示得到同一窗口；
不同日期的同一时段不会合并。时间缺失、无效或没有时区时，继续使用原有
未知时间用户分组，不根据文件名、运行时间或机器时区猜测 capture 时间。
缺失用户与字面值 `no_user_id` 保持既有身份区分。真实 session 不受窗口影响。

窗口在 Spark 汇总和 shuffle 前确定。窗口内继续做精确前缀聚合和结构化
子代理挂载；跨窗口不折叠前缀、不挂载子代理、不补接边界。跨边界的同一真实
对话可能保留多个片段或重复历史，这是本次选择的截断聚合边界。窗口参与
缺失-session 轨迹身份，避免相同正文跨窗口产生相同输出文件名；输出仍使用
`session_id="no_session_id"`，不会伪造真实 session。

新 Spark manifest 额外写入 `sessionless_window_hours: 8`，用于明确文件名和
lineage ID 的计算规则。没有这个标记的历史产物及普通 Python 产物按原有身份
规则校验；普通 Python 写入仍使用原有规则，不启用时间切片。

同一用户一个北京时间自然日最多有三个有时间窗口，未知时间输入另保留原有
回退分组。三个窗口可能数据量不均，也可能落在同一执行分区；窗口内仍可能
很大，因此不保证三倍并行度、三倍提速或固定内存占用。磁盘索引、预算检查和
既有失败边界继续有效。
